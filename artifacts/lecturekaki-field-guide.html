The one idea to hold onto

Everything is serverless and stateless. A Lambda runs for one request or event and then stops, remembering nothing. Anything that has to last lives in a managed service: files in S3, records in DynamoDB, open sockets in API Gateway, users in Cognito. That's why it scales by itself, and why you pay only for what is used.

Part 1

Static site and sign-in

How the page reaches the browser, and how a student proves who they are.

Dashed arrow = a response or redirect coming back.

Loading the site
  • 1
    The browser asks CloudFront for the page. CloudFront is AWS's CDN: copies are cached in edge locations near the user. A small CloudFront Function (JavaScript that runs at the edge on every request) rewrites React page paths such as /forum/… or /timetable to /index.html. Without it, refreshing on /forum would give a 404, because there's no file called "forum" in S3. Paths under /assets/ and /lectures/ pass through unchanged. HTTP is redirected to HTTPS, and AWS's managed security-headers policy is added to every response.
  • 2
    CloudFront fetches from S3 using OAC. The web bucket blocks all public access. Its bucket policy lets exactly one caller read: the CloudFront service, and only when the request comes from our distribution (AWS:SourceArn condition). OAC (Origin Access Control) means CloudFront signs each request to S3 with SigV4. So nobody can bypass the CDN and read the bucket directly.

Caching, in one sentence each

assets/* (built JS/CSS with hashed filenames) are cached for a year as immutable, because a new build gets new filenames. index.html is no-cache, so a deploy shows up immediately. Lecture snapshot files are cached for 1 day as immutable, and the lectures/current.json pointer is no-cache (see Part 5). CloudFront's cache policy has a default TTL of 0, so it follows whatever Cache-Control header each S3 object carries.

Signing in
  • 3
    The browser redirects to Cognito's hosted login page using the authorization code flow with PKCE (frontend/src/features/forum/auth.ts). Before redirecting, the app creates two random values. code_verifier stays secret in the tab, and its SHA-256 hash (code_challenge, method S256) is sent to Cognito. state is also sent and is checked when the browser comes back, which blocks forged login responses (CSRF).
  • 4
    On sign-up, Cognito calls the pre-signup Lambda. It checks the email against a regex for …@u.nus.edu. Any other address raises an error, and Cognito refuses the account. Users also confirm their email with a code.
  • 5
    Cognito redirects back to /auth/callback?code=…&state=…. The app checks that state matches, then POSTs the code plus the original verifier to Cognito's /oauth2/token. Cognito hashes the verifier and compares it with the challenge from step 3. A stolen code is therefore useless without the verifier. It returns an access token (15 min), an ID token and a refresh token (30 days).
  • 6
    Every API call carries Authorization: Bearer <access token>. Tokens live in sessionStorage, so each tab has its own and they're gone when the tab closes. A non-secret cookie only remembers "this browser signed in before", and a localStorage value tells other tabs when you log out.
  • 7
    API Gateway invokes the FastAPI Lambda (details in Part 2).
  • 8
    FastAPI verifies the token itself (backend/app/modules/auth/dependencies.py). It downloads Cognito's public signing keys (JWKS) once and caches them, then checks: algorithm is RS256 and the signature is valid, not expired, the issuer is our user pool, client_id is our app, token_use is access (an ID token is rejected), and sub is present. The sub (a stable user ID) becomes the user ID for timetables, topics and message authors. A bad token gets 401. If keys or configuration are unavailable, it gets 503.

Logging out

The app clears local tokens, asks Cognito to revoke the refresh token (/oauth2/revoke) and ends the hosted session. An access token that was already issued stays valid until it expires (at most 15 min), because JWTs are checked offline. That's the usual trade-off with short-lived JWTs.

Part 2

REST API and storage

One FastAPI app, packaged into one Lambda, behind one catch-all API Gateway route.

  • 1
    The browser sends an ordinary HTTPS request to the HTTP API's execute-api URL, for example PUT /timetable/semesters with the JWT in the header. The browser first checks CORS: FastAPI's CORSMiddleware only allows our website origins and the methods GET/POST/PUT/DELETE.
  • 2
    API Gateway has a single route, $default, with an AWS_PROXY integration. It doesn't route anything itself. It packs the whole request (method, path, headers, body) into a JSON event and invokes the Lambda. Inside the Lambda, Mangum turns that event into an ASGI request, FastAPI routes it to the right function, and Mangum turns the response back into JSON that API Gateway sends to the browser. Locally, uvicorn replaces Mangum and the FastAPI code is unchanged. The Lambda has a 29-second timeout because API Gateway gives up at 30.
  • 3
    Timetable (modules/timetable): one DynamoDB item per user (key user_id = Cognito sub), holding a "book" of four semesters' lesson selections. Saving replaces the whole item, so the last write wins. Endpoints: GET/PUT /timetable/semesters (the older /timetable routes still work).
  • 4
    Profile (modules/profile): interest topics (an ordered list) and username, stored in the profiles table (also keyed by user_id). PUT /profile/topics keeps the order and drops duplicates. Signed out, topics live in localStorage. On sign-in, browser topics are copied up only if the account has none.
  • 5
    Forum (modules/forum): messages, upload records, tickets and connections all live in one table using the single-table pattern (see Data model). Details are in Parts 3 and 4.
  • 6
    PDFs: the API never streams file bytes to or from the browser. It hands out short-lived presigned URLs and only reads the file once, to check it (Part 3).
  • 7
    NUSMods: when you save a timetable, the backend fetches each module from api.nusmods.com/v2 and checks your selections really exist (right semester, right lesson type and class number). Responses are capped at 5 MB. A user can't save made-up lessons by calling the API directly.
  • 8
    Some data never touches our API. The Timetable page downloads NUSMods' moduleList.json straight from the browser for "Add a module" search, and Discover reads lecture JSON from CloudFront. Both searches run entirely in the browser.

Part 3

Forum: messages and PDF attachments

One room per lecture session. Posting is plain HTTP; PDFs go straight between the browser and S3.

What a "room" is

Every lecture session (one module, one date, one time, one venue) has its own room. The room ID is built from the session ID plus the term:

CS2040-LEC-1@2026-11-17-1000-LT19@2026-2027@1
└─ module ─┘ └type┘└class┘ └── date ──┘ └time┘ └venue┘ └acad year┘ └sem┘

The browser only shows rooms that exist in the current lecture catalogue. The backend checks the ID's format, date, time and academic year. A room closes at Sunday 23:59 Singapore time of its lecture's week. After that, room_closes_at in forum/service.py makes the API return 403 for reading, posting, uploading and tickets, so a hand-typed URL can't get around the UI.

Read top to bottom. Dashed = response going back. The PDF part is optional; a plain message is just steps 8–10.

Uploading a PDF
  • 1
    Ask to upload. The browser sends the filename (must end in .pdf, no slashes or control characters) and the size (1 byte to 15 MB).
  • 2
    Quota and record. A PDFQUOTA#<user>#<hour> counter allows at most 10 uploads per user per hour; past that, the API returns 429. Then it saves UPLOAD#<id> with the room, author, size and the S3 key uploads/<room's closing date>/<id>.pdf. The record expires after 10 minutes if it isn't used.
  • 3
    Presigned PUT URL. The API signs a URL that allows exactly one thing for 60 seconds: PUT to that key, with that content type, that exact size, and If-None-Match: * (only if the object doesn't already exist).
  • 4
    The browser uploads straight to S3. The file never passes through Lambda, which keeps Lambda fast and cheap and avoids API Gateway's payload limits. The bucket's CORS rules allow PUT only from our website origins.
  • 5–7
    Check the file. The browser asks for the upload's status. The API reads the object's metadata (it needs a version ID, because the bucket is versioned), then reads that exact version. It checks that the size and type match, the file starts with %PDF-, pypdf can parse it, it isn't encrypted, and it has 1–1000 pages. Only then is the upload marked ready and that version ID recorded. At most 2 checks run at once per Lambda; beyond that it returns "busy, retry" (429).
Posting
  • 8
    Post. Text must be 1–500 characters. The room must be open.
  • 9
    One DynamoDB transaction does two things together: marks the upload as claimed (only if it belongs to this room and author, has the validated version, hasn't expired and isn't already claimed) and writes ROOM#<room> / MSG#<id>. Either both happen or neither does, so one PDF can't be attached to two messages. Messages get expires_at and ttl set to the room's closing time.
  • 10
    201 Created. Right before replying, FastAPI hands the "new message" event to the fan-out Lambda, covered in Part 4.
Downloading
  • 11–13
    Presigned GET. The API signs a URL for the exact version it validated, valid for 60 seconds or until the room closes, whichever is sooner. It forces a download (Content-Disposition: attachment, application/octet-stream, no-store), so the browser never renders it inline. The browser opens that URL directly.

Deleting and expiry

Delete: only the author can delete (the API compares the message's author with your token's sub; anyone else gets 403). It deletes the message (a conditional delete, so a race returns 404), broadcasts message.deleted, then deletes the attached PDF version from S3.

Expiry: messages disappear through DynamoDB TTL (eventually; reads already hide them). PDFs are deleted by the Monday cleanup job (Part 5). Reading history uses cursor-based pages of at most 100.

Part 4

Live forum updates

The socket is only used to receive updates. All writes still go through HTTP.

Read this first

A Lambda can't hold a connection open: it runs and then stops. So API Gateway's WebSocket API keeps every socket open and gives each one an ID such as abc123. When something happens on a socket (connect, a message, disconnect), API Gateway calls the live Lambda briefly. When we want to send something to a browser, any Lambda calls API Gateway's PostToConnection(abc123, data). DynamoDB records which connection IDs are in which room.

A · Get a ticket
  • 1
    Ask for a ticket over HTTP, with the normal Authorization: Bearer JWT. FastAPI checks the token and that the room is open.
  • 2
    Save the ticket. It's 32 random bytes (secrets.token_urlsafe), stored hashed as TICKET#… with the room, user and token expiry. It expires in 30 seconds.
  • 3
    Return a ready-to-use URL: wss://<id>.execute-api…/live?room=…&ticket=….
    Why a ticket? The browser's new WebSocket(url) can't set an Authorization header, so login proof has to go in the URL. URLs get logged, so we don't put the 15-minute JWT there. A ticket works once, for 30 seconds, for one room, and only for opening a socket.
B · Open the socket
  • 4
    new WebSocket(url) sends an HTTP GET with Upgrade: websocket. API Gateway holds that request and doesn't answer yet.
  • 5
    API Gateway calls the live Lambda with route $connect, passing the new connection ID, the query string and headers.
  • 6
    The live Lambda checks and records. If the Origin isn't our site it returns 403. It uses up the ticket with a conditional delete: the delete only succeeds if the ticket exists, matches the room and hasn't expired, so it can never be used twice. If that fails it returns 401. Then it writes CONN#abc123 = {room, user, token expiry}. This is pending: the connection exists but isn't in the room yet.
  • 7–8
    Returning 200 means "allow". API Gateway then answers the browser with 101 Switching Protocols, the socket is open, and the browser fires onopen. With 401/403/503 the socket never opens, and the browser retries after 1 s, 2 s, 4 s … up to 30 s, each time with a new ticket.
C · The ready handshake
  • 9
    Inside onopen the browser sends {"action":"ready"} and starts a 10-second timer.
  • 10–11
    API Gateway routes it as $default. The live Lambda runs activate_connection, a DynamoDB transaction that checks CONN#abc123 still exists and adds ROOM#<room> / CONN#abc123. From now on, fan-out will send to Bob.
  • 12–13
    The Lambda acknowledges with PostToConnection → {"type":"ready"}. The browser clears the timer, reloads history over HTTP, shows any events that arrived meanwhile (de-duplicated by message ID), and only then shows "connected".

Why the extra "ready" step exists (PR #30)

$connect runs before API Gateway has finished opening the socket. If the connection were added to the room at step 6 and someone posted right then, PostToConnection would fail with GoneException. The code treats that as "user left" and would remove Bob, who would then never get live messages. A ready message can only arrive over an open socket, so receiving it proves the socket works. Only then is Bob added to the room.

D · Someone posts
  • 14–15
    Alice posts over HTTP and FastAPI saves the message (Part 3). It is now stored safely.
  • 16
    FastAPI hands off delivery with lambda.invoke(InvocationType="Event"). That means "queue this and don't wait": AWS returns 202 immediately and runs the fan-out Lambda separately. If this hand-off fails, the post still succeeds; FastAPI logs "Forum broadcast could not be queued", which raises an alarm (Part 6).
  • 17
    Alice gets 201 straight away, even if the room has 200 people in it.
  • 18
    Fan-out re-reads the message (skips it if it was deleted or expired in the meantime) and queries every ROOM#<room> / CONN#*.
  • 19–20
    PostToConnection for each connection, 16 at a time. API Gateway pushes the data down each socket. A connection whose token has expired is closed. GoneException means the person left, so their record is deleted. Any other error makes the Lambda fail on purpose, so AWS retries it twice. After that, the event goes to SNS and the team gets an email.

Keeping the socket healthy

SituationWhat happens
No traffic for a whileBrowser sends {"action":"ping"} every 4 min (API Gateway closes idle sockets after 10 min)
Access token about to expireBrowser closes the socket ~5 s before expiry and reconnects with a fresh token and ticket
Socket open 2 hoursAPI Gateway's hard limit; the browser reconnects
Tab closedAPI Gateway calls the live Lambda with $disconnect, which deletes the connection records. If that's missed, DynamoDB TTL removes them later
Running locallyNo WebSocket API or fan-out: FastAPI serves /rooms/{id}/live and an in-memory hub broadcasts (single process only)

The rule that makes this safe

DynamoDB is the source of truth; the socket is a convenience. If a push is ever lost (for example the Lambda crashes between saving and handing off), the message is still stored, and the browser reloads history every time it (re)connects.

Part 5

Weekly jobs

Lecture data is pre-built once a week into static JSON. A second job deletes old PDFs.

Lecture ingestion (Monday 03:00 SGT)
  • 1
    EventBridge Scheduler starts the ingest Lambda (cron(0 3 ? * MON *), Asia/Singapore). It works out today's semester from the hard-coded academic calendar (AY2026/27), then decides whether a run is due: Mondays of teaching weeks 1–3, or the first Monday of a month. Otherwise it logs "skipped". A manual run with {"date": "…"} always runs.
  • 2
    Fetch from NUSMods: moduleInfo.json for the year and venueInformation.json for the semester, retrying up to 3 times. It keeps only Lecture lessons (not tutorials or labs, and no NUS-ISS courses), then expands "Monday, weeks 1–13" into real dates using the calendar (skipping recess week and public holidays), with times in Singapore time.
  • 3
    Topics. First, keyword rules on the module title. Then Amazon Bedrock (Nova 2 Lite) reads each description and suggests extra topics as numbers from a fixed list (numbers use fewer tokens). A model topic is kept only if one of that topic's keywords appears in the module's title or description, because a wrong topic is worse than a missing one. There are at most 3 topics per module. Answers are cached in lectures/topic-cache.json by model, topic list and module text, so a weekly run only sends new or changed modules.
  • 4
    Publish to S3, but only if something changed. It builds the whole snapshot in memory and computes one SHA-256 fingerprint of all its files (leaving out generatedAt and the random folder name). If that matches contentHash in the live current.json, it writes nothing except a new checkedAt time, and the result says "unchanged": true. Otherwise it writes a full snapshot folder first, then switches the pointer lectures/current.json (explained below). A manual run with {"force": true} publishes anyway.
  • 5
    CloudFront serves those JSON files. Discover loads current.json, follows its path, and loads the week or day it needs. No API call and no database.
lectures/
├── current.json                ← pointer + contentHash + checkedAt, no-cache   (written LAST)
├── topic-cache.json            ← Bedrock answers
└── <snapshot>/                  ← Cache-Control: public, max-age=86400, immutable
    ├── index.json
    ├── modules.json            ← module details + topics
    ├── weeks/<label>.json       ← e.g. week-07.json
    └── days/<yyyy-mm-dd>.json

Why the pointer pattern

Browsers never see a half-written update. They keep reading the old snapshot until the single small current.json changes, and then they see the new one. Snapshot files never change after they're written, so they can be cached hard. Rollback = point current.json back at an older snapshot.

Why the fingerprint (PR #37): most weekly runs find identical data. Skipping the write means no duplicate snapshot folders, and browsers and CloudFront keep their cached files. generatedAt now means "when the data last changed"; Discover shows checkedAt ("last checked"), falling back to generatedAt. The hash only says whether anything changed, not which file.

Safety checks: empty data is never published. A re-run of the same semester with fewer than half the previous sessions is rejected. A new semester that small is published (the old term is over) but logs SMALL_NEW_SEMESTER, which raises an alarm.

PDF cleanup (Monday 00:05 SGT)
  • 6
    The scheduler starts the cleanup Lambda five minutes after the week has rolled over.
  • 7
    It lists every version under uploads/. The folder name is the room's closing date, so any folder whose date has passed belongs to closed rooms. It deletes all versions and delete markers there, in batches of 1000, including uploads that were never posted. If any delete fails, the Lambda raises an error so the alarm fires. Its IAM role can only list and delete under uploads/.

Known limits

The calendar only covers AY2026/27; from August 2027 ingestion fails with "No calendar entry…" and the ingest alarm fires. Special terms aren't ingested. Between terms (for AY2026/27, 23 Nov 2026 – 3 Jan 2027) every week is past, so Discover says the term has ended. Semester 2 is published on Monday 4 Jan 2027.

Data model

Three DynamoDB tables, all on-demand billing (PAY_PER_REQUEST), plus two S3 buckets.

Forum table: one table, many record types

The table has a generic partition key PK and sort key SK. Each record type uses a prefix, so one table holds everything, and one query on PK = ROOM#x can fetch a room's messages (SK begins with MSG#) or its connections (SK begins with CONN#). A ttl attribute lets DynamoDB delete old records for free.

Rehearsal

Questions a TA is likely to ask

Why serverless instead of EC2 or containers?
Usage is spiky (around lecture times) and low most of the time. Lambda and on-demand DynamoDB cost nothing when idle and scale automatically, and there are no servers to patch. The project used to run on a Caddy server and moved to Lambda.
How does it scale?
Lambdas keep no state between requests, so AWS runs as many copies as needed. Sockets are held by API Gateway and room membership is in DynamoDB, so any Lambda copy can broadcast. Static content is served from CloudFront's cache. The limits are Lambda concurrency, API Gateway quotas, and fan-out work that grows with room size.
Why is lecture data static JSON and not an API?
It changes weekly and is identical for everyone. Pre-built files behind a CDN are the fastest and cheapest option and don't touch the backend at all. Search runs in the browser.
What is Mangum?
An adapter inside the FastAPI Lambda. It converts API Gateway's event into an ASGI request for FastAPI and converts the response back. The same app runs under uvicorn locally.
Why a ticket for the WebSocket?
Browsers can't set headers on new WebSocket(), and a JWT in a URL could be logged. A ticket is single-use, lasts 30 s, works for one room, and can only open a socket.
Why the ready handshake?
$connect runs before the socket is fully open. Joining the room only after ready means a broadcast can't hit a half-open socket and wrongly remove a user.
Can a message be lost?
The message can't: it's saved before anything else. A live notification can be, rarely (a crash between saving and handing off). The client reloads history on every (re)connect, and a failed hand-off raises an alarm.
Why does the browser upload PDFs directly to S3?
It keeps large bodies out of Lambda and API Gateway (cheaper, no payload limits). The presigned URL is locked to one key, one size, one content type, 60 s, and no overwrite. The server still checks the file before it can be posted.
How is security handled?
NUS-only sign-up; PKCE login; offline JWT checks (RS256, issuer, client, token_use); ownership checks on delete; rooms closed by date on the server; single-use tickets; short presigned URLs; private S3 via OAC; least-privilege IAM role per Lambda; CORS restricted to our origins; OIDC deploys with no stored keys.
How do you know when something breaks?
9 CloudWatch alarms → SNS → email: Lambda errors, API 5xx, and three log-based checks.
Where is AI used?
Only in weekly ingestion: Bedrock Nova 2 Lite adds topics, checked against keywords and cached so unchanged modules aren't sent again.
What would you improve?
Make the academic calendar data-driven instead of hard-coded; move the remaining CloudFormation stacks into Terraform; add a custom domain; load-test fan-out for large rooms.
